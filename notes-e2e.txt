Aula 1:

o que são sistemas complexos?

R: sistemas constantemente influenciados pelo ambiente onde operam. Ex: Influenciada por como o usuario utiliza, local onde utiliza, influenciadas por passagem de tempo, regulações. 

O que são as leis de Lehman?

R:  são princípios que descrevem a evolução d sistemas complexos. 3 que são importantes são:

1 - Mudança continua
Um software precisa se adaptar continuamente. Se não se adaptar, sua utilidade e satisfação diminuirão com o tempo, à medida que o ambiente e as necessidades dos usuários evoluem.

2 - Complexidade Crescente
Com cada alteração em um software, sua complexidade tende a aumentar, a menos que esforços específicos sejam feitos para contrabalançar esse crescimento. Isso pode levar a um aumento nos custos de manutenção e desenvolvimento ao longo do tempo.


3 - Qualidade em declinio
Sem uma manutenção e adaptação rigorosas às mudanças no ambiente operacional, a qualidade do software tende a declinar ao longo do tempo, à medida que as expectativas dos usuários e as demandas do mercado evoluem.

dica: é sempre bom começar os testes pelos casos de erro. o caso de erro parte de validações feitas no codigo, o codigo nao precisa ser configurado muito pra ter informações extras pq vc ja sabe q vai lançar erro

dica: começar pelos testes mais simples primeiro

dica: no script de teste e2e, colocamos a flag  --test-concurrency=1 garante que so tem 1 processo executando os testes, isso faz com que os testes nao executem em paralelo. Foi necessario pq como os testes compartilham do mesmo banco, um interfere no outro. ex: um teste que depende do banco vazio é afetado por um teste que preenche dados no banco.

dica: separar um banco de dados so pra testes, que é uma copia do banco de dev. isso é necessario pro banco de dev nao ficar poluido. o scrips em docker/init/02-create-test-db.sql cria esse banco. o banco de dev é transformado em um template e o banco de dev é criado conforme esse template. no script de teste e2e, o env-file usa o .env.test. nesse arquivo .env.test tem a url do banco de teste

dica: não criar testes somente a nivel de api, mas tambem a nivel de banco, verificando se os dados do banco sao compativeis com o retorno esperado. 

dica: pra criar dados que vao ser necessarios pro teste, use sempre os endpont da api, nao crie direto no banco. Isso por que, se a api tiver com bug, o teste vai falhar ja no cadastro desses dados. Caso os dados sejam cadastrados direot via banco, esses bug da api podem passar


Teste caixa preta: 
 - se preocupa apenas com a entrada e saida da api.
 - menor proteção contra regressão (bugs)
 + resistencia a refatoração (tanto faz os controllers, services, e outros detalhes de implementação)

Teste caixa cinza: 
 - se preocupa com a entrada e saida da api, mas também com os dados do banco
 - maior proteção contra regressão 
 - menor resistencia a refatoração (se a tabela ou colunas mudarem, o teste vai falhar)
